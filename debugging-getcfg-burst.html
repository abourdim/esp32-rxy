The GETCFG burst bug

How the ESP32 esp32-rxy firmware's Bluetooth layout transfer stalled forever, why six reasonable fixes didn't work, and what actually fixed it. Fixed in cdaac4f.

The symptom

The bit-rxy web app connects to the ESP32 over Bluetooth, sends GETCFG, and expects the firmware to stream back the remote's layout as ~60 small CFG chunks followed by CFGEND. Instead, the app's loading overlay hung forever on Receiving layout... (N) — and N kept landing on the same number, over and over, no matter what changed.

The tell: a hard, content-independent ceiling — often exactly 17 of the ~60 chunks — reproduced across firmware rebuilds, reboots, and even completely different layouts. That kind of exact repeatability usually means a structural bug, not random radio flakiness.

Turning on NimBLE's own internal error logging (CONFIG_NIMBLE_CPP_LOG_LEVEL) showed the mechanism directly: the firmware's own notify()/indicate() calls were returning rc=6 — BLE_HS_ENOMEM, "not enough memory" — on almost every packet of the burst.

Six reasonable fixes that didn't work

Each of these was a genuine, well-supported hypothesis for what could cause a Bluetooth stack to run out of send buffers mid-burst. Each was implemented, tested on real hardware, and ruled out in turn.

  1. MTU too small (or too large)

    The default BLE MTU (23 bytes, ~20 usable) is barely too small for a 23-byte CFG <18-char>\n line. Requested a larger MTU via setMTU(247).

    Result: identical rc=6 cascade, starting at the identical chunk. Tried setMTU(64) instead — same result. Tried no explicit setMTU() call at all, letting NimBLE's own built-in default (255) stand — same result again. MTU was never the variable.

  2. notify() vs indicate()

    Indications get acknowledged by the central; notifications don't. Switched the TX characteristic to INDICATE and added a real wait for the acknowledgment via NimBLE's onStatus() callback — which fires from the actual asynchronous BLE_GAP_EVENT_NOTIFY_TX completion event, not just a synchronous "did the call queue?" guess.

    Result: failed identically. Some packets even came back explicitly nacked — most likely because Web Bluetooth's startNotifications() only ever enables the notify bit in the CCCD, not indicate, even on a characteristic that supports both.

  3. Retrying failed sends

    notify()'s boolean return value seemed like a reasonable thing to check and retry on when it reported failure.

    Result: actively harmful. The return value turned out to be an unreliable signal on this stack — some packets it reported as "failed" had actually gone out over the air anyway. Retrying on it re-sent already-delivered chunks, and the app's own received-chunk counter was observed exceeding the real total (duplicate data corrupting the stream).

  4. Connection interval too slow to drain the queue

    If the negotiated BLE connection interval is too long, the radio can't physically transmit queued packets fast enough to free up send buffers. Requested a fast 7.5–15 ms interval via NimBLEServer::updateConnParams() right on connect.

    Result: no change.

  5. The demo-output loop racing the CFG burst

    The firmware's loop() pushes periodic demo values (led_demo, gauge_demo, …) once a second. Since that runs on a different task than the code handling an incoming BLE write, it seemed plausible the two were colliding on the same characteristic mid-burst. Added a gSendingCfg flag to gate the demo output off for the duration of a transfer.

    Result: good hygiene, kept in the final fix — but not what was causing rc=6.

  6. Arduino-ESP32 core / BLE controller version

    The default-resolved core (2.0.9, based on ESP-IDF 4.4) ships a BLE controller build with CONFIG_BT_CTRL_BLE_STATIC_ACL_TX_BUF_NB=0 — zero static ACL transmit buffers. That looked like a smoking gun. Pinned the build to a newer core (2.0.14, IDF 5.x) to test.

    Result: same rc=6 cascade — and the exact same config value turned out to be present on both core versions. Red herring. (The version pin was kept anyway, since it's the combination the firmware is now actually tested against.)

Stepping back: an isolated test

After six independently reasoned fixes all failed in exactly the same way, continuing to patch the ~700-line application stopped being productive. The next step was to stop guessing inside the full app and build a platformio_ble_probe/ — a separate, minimal PlatformIO project with no CFG protocol, no demo loop, no app logic at all. Just: on connect, blast some small notify() calls, and log exactly what happens.

TestWhat it didResult
Probe v1 Arbitrary 18-byte payloads, burst fired from loop() on a 1-second timer after connect. 60 / 60 succeeded. The chip and the library are fine on their own.
Probe v2 Real CFG payload and CFGBEGIN/CFG/CFGEND framing, burst fired from inside the RX characteristic's onWrite() callback in response to a real "GETCFG" write — structured exactly like the real firmware. 17 / 60 — failed identically to the real firmware, rc=6 and all.
Probe v2, one change Same as above, except onWrite() now just sets a flag, and loop() reads that flag and runs the burst itself. 60 / 60 succeeded.
That one variable — which task the burst runs from — was the whole bug. Nothing about MTU, notify/indicate, retries, connection interval, or core version ever mattered.

The actual root cause

RxCallbacks::onWrite() — the function that reacts to an incoming BLE write, i.e. the app's GETCFG — runs on NimBLE's own host task, not the ordinary Arduino loop() task. The original code called sendCfg() directly from inside that callback: a ~900 ms loop of 60 notify() calls, each followed by a 15 ms delay().

That meant the BLE host task was still "inside" the app's own code for the entire burst. It never got a chance to return to its own event loop and process its own buffer-completion housekeeping — freeing send buffers once the radio confirms a packet has actually gone out over the air. With that housekeeping blocked for 900 ms straight, the buffer pool had no way to drain, and every notify() past the first handful failed with ENOMEM.

This is a well-known class of bug in event-driven and RTOS-based systems in general: never do slow, blocking work synchronously inside a callback that runs on a task you also depend on to make forward progress. The callback and the resource it starves were the same task — so nothing could ever recover on its own.

The fix

Before

// runs on NimBLE's host task
if (line == "GETCFG") {
  sendCfg();   // blocks the host
  return;
}

After

// runs on NimBLE's host task
if (line == "GETCFG") {
  gGetCfgRequested = true;
  return;       // returns immediately
}

// runs on the main Arduino task
void loop() {
  if (gGetCfgRequested) {
    gGetCfgRequested = false;
    sendCfg();  // host task is free
  }
  ...
}

handleLine() no longer calls sendCfg() when it sees GETCFG — it just sets a flag. loop(), running on the ordinary Arduino main task, checks that flag once per iteration and runs the burst from there instead. The BLE host task is now completely free during the whole transfer to do its own bookkeeping concurrently, so the buffer pool never starves.

With that fixed, plain NOTIFY — no indicate(), no retry loop, no wait-for-ack machinery — turned out to be perfectly reliable. None of the complexity from hypotheses 2–4 above was ever actually needed; it was all working around a symptom of the real bug rather than the bug itself.

Lessons

  • A deterministic, content-independent failure point is a structural clue, not noise. The same "17 of 60" recurring across completely different test conditions was the strongest signal in the whole investigation — worth trusting earlier.
  • Enable the library's own error logging before guessing. CONFIG_NIMBLE_CPP_LOG_LEVEL turned "notify failed, no idea why" into an exact, real error code — the single most useful step in the whole process, and it should have come first.
  • A return value isn't proof of delivery, and isn't proof of failure. notify()'s boolean result was demonstrably wrong in both directions on this stack. Don't build retry logic on a signal you haven't independently verified.
  • When several independent, well-reasoned fixes all fail identically, stop patching the full application. Build the smallest possible thing that can reproduce the bug in isolation. The probe found in minutes what six rounds of in-app changes couldn't.
  • Never block inside a callback that runs on a task you depend on. If a callback needs to do slow work, hand it off (a flag, a queue, a semaphore) to a different task instead of doing the work in-place.
